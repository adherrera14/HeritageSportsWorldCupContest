Guia de Integracion con Base de Datos para Produccion

Plan practico y facil de seguir para migrar de JSON estatico y almacenamiento del navegador a una arquitectura segura de produccion.

Alcance: aplicacion del concurso y leaderboard. La pagina de admin actual es solo demo y no debe incluirse en el despliegue de produccion.

Estado Actual (Revisado)

  • El frontend carga datos desde data/*.json y calcula puntajes en JavaScript del navegador.
  • Los picks del usuario y el estado de bloqueo se guardan en localStorage.
  • La etapa del torneo tambien se controla desde localStorage.
  • El leaderboard se inicializa desde JSON estatico y luego se recalcula en el cliente.

Objetivos de Produccion

  • Fuente unica de verdad en la base de datos.
  • Calculo de puntajes y leaderboard del lado del servidor.
  • Picks autenticados por usuario con auditoria.
  • Flujo interno del equipo dev para actualizar resultados y etapas.

Reglas No Negociables

Importante No desplegar admin.html en produccion.

La administracion de resultados y el avance del torneo debe hacerse por el equipo dev mediante procesos backend controlados.

1) Arquitectura Objetivo

  • Frontend: las paginas existentes consumen endpoints REST en lugar de archivos JSON.
  • Backend API: autenticacion, picks, datos por etapa, resultados y leaderboard.
  • Base de datos: se recomienda PostgreSQL por consistencia transaccional y consultas robustas.
  • Jobs o Workers: opcionales para snapshots del leaderboard e invalidacion de cache.
  • Ops: desplegar frontend y API por separado, y proteger rutas internas de actualizacion.

2) Modelo de Datos Recomendado

Tabla Proposito Columnas Clave
teams Lista maestra de 48 equipos id, code, name, group_code, is_active
tournament_stages Definicion de etapas y etapa actual id, stage_key, display_name, sequence, is_current
matches Resultados oficiales por etapa id, stage_id, home_team_id, away_team_id, winner_side, home_score, away_score
users Participantes del concurso id, email, username, created_at
user_picks Un valor de ranking por equipo y usuario id, user_id, team_id, rank_value, locked_at
score_events Eventos inmutables de puntuacion id, user_id, match_id, team_id, points_awarded, created_at
leaderboard_snapshots Vista de lectura rapida por etapa id, stage_id, user_id, total_points, rank, calculated_at
audit_logs Trazabilidad de acciones del equipo dev id, actor, action, payload_json, created_at

3) Mapeo de JSON a Base de Datos

  • data/teams.json -> seed de teams.
  • data/stage-*.json -> seed de tournament_stages y matches.
  • data/leaderboard.json -> bootstrap opcional historico; en produccion el leaderboard debe salir de datos calculados, no de seed estatico.
  • Valores de localStorage -> migrar a user_picks y sesion autenticada.

4) Contrato de API (Sugerido)

Endpoints Publicos de Usuario

  • GET /api/v1/teams
  • GET /api/v1/stages/current
  • GET /api/v1/stages/{stageId}/matches
  • GET /api/v1/leaderboard?stageId={id}&limit=20
  • GET /api/v1/me/picks
  • PUT /api/v1/me/picks
  • POST /api/v1/me/picks/lock

Endpoints Internos del Equipo Dev (Protegidos)

  • POST /internal/v1/stages/{stageId}/activate
  • POST /internal/v1/matches/{matchId}/result
  • POST /internal/v1/leaderboard/rebuild

5) Ubicacion de la Logica de Puntajes

Regla La puntuacion debe ejecutarse solo en el servidor.

  • Por cada partido finalizado, determinar ganador: home, away o draw.
  • Si es empate: otorgar 0 puntos a todos los usuarios para ese partido.
  • Si hay ganador: sumar el valor rank_value del equipo ganador desde user_picks al total de cada usuario.
  • Guardar cada calculo como fila en score_events para trazabilidad.
  • Recalcular o actualizar incrementalmente leaderboard_snapshots.

6) Plan de Implementacion Paso a Paso

Paso 1: Baseline y Congelamiento

  1. Congelar el esquema JSON actual y validar resultados de scoring como fixtures de referencia.
  2. Documentar nombres e IDs de etapa usados por el frontend.

Paso 2: Base de Datos y Migraciones

  1. Crear migraciones para las tablas principales definidas arriba.
  2. Agregar restricciones unicas: un pick por (user_id, team_id) y un rank por (user_id, rank_value).

Paso 3: Scripts de Seed e Importacion

  1. Importar equipos y resultados de etapa desde los JSON existentes.
  2. Cargar usuarios de ejemplo solo en ambientes no productivos.

Paso 4: API y Autenticacion

  1. Agregar autenticacion de usuarios (sesion o JWT).
  2. Implementar endpoints de picks y lock con validaciones del lado servidor.
  3. Agregar endpoints internos para actualizar etapas y resultados.

Paso 5: Mover Scoring al Backend

  1. Portar reglas de puntuacion del frontend a la capa de servicios.
  2. Agregar pruebas deterministicas con fixtures de etapas conocidas.

Paso 6: Refactor del Frontend

  1. Reemplazar todas las llamadas fetch('data/*.json') por llamadas a la API.
  2. Eliminar localStorage como fuente de verdad (dejarlo solo para preferencias no criticas si hace falta).
  3. Conservar UI y reglas actuales del concurso mientras cambia la fuente de datos.

Paso 7: Despliegue y Cutover

  1. Ejecutar dual-read en staging y comparar respuestas API contra comportamiento JSON actual.
  2. Activar feature flag de modo base de datos en produccion.
  3. Deshabilitar JSON de runtime una vez verificada la integracion.

7) Ejemplo de Restricciones SQL

-- Un rank por equipo para cada usuario
CREATE UNIQUE INDEX ux_user_picks_user_team
ON user_picks (user_id, team_id);

-- Un rank unico (1..48) por usuario
CREATE UNIQUE INDEX ux_user_picks_user_rank
ON user_picks (user_id, rank_value);

-- Validacion opcional
ALTER TABLE user_picks
ADD CONSTRAINT chk_rank_value_range CHECK (rank_value BETWEEN 1 AND 48);

8) Checklist de Seguridad y Operacion

Requerido Minimo para estar listo para produccion:

  • Proteger endpoints internos con RBAC y, si es posible, allow-list de IP.
  • Usar consultas parametrizadas u ORM para prevenir inyeccion SQL.
  • Configurar backups de base de datos y pruebas de restauracion.
  • Activar logs estructurados para cambios de resultados y recalculos.
  • Monitorear latencia API, conexiones DB y fallas en jobs de scoring.
  • Ejecutar migraciones en CI/CD; nunca cambios manuales de schema en produccion.

9) Riesgos Altos Detectados en la Implementacion Actual

  • El scoring y el avance de etapa del lado cliente pueden manipularse editando almacenamiento del navegador.
  • Los valores del leaderboard no son autoritativos porque se calculan en el navegador.
  • Scripts inline y datos estaticos dificultan control de acceso y auditoria.
