World Cup Contest Production Database Integration Guide

Easy-to-follow implementation plan to move from static JSON and browser storage to a secure production architecture.

Scope: Contest app and leaderboard only. The current admin page is demo-only and must not be part of production deployment.

Current State (Reviewed)

  • Frontend loads data from data/*.json and computes scoring in browser JavaScript.
  • User picks and lock status are saved in localStorage.
  • Tournament stage is also controlled from localStorage.
  • Leaderboard entries are seeded from static JSON, then recalculated client-side.

Production Goals

  • Single source of truth in database.
  • Server-side scoring and leaderboard calculations.
  • Authenticated user picks with audit trail.
  • Internal dev-team workflow for score and stage updates.

Non-Negotiables

Important Do not deploy admin.html to production.

Score administration and tournament progression must be done by the dev team through backend-controlled processes.

1) Target Architecture

  • Frontend: existing pages consume REST endpoints instead of JSON files.
  • Backend API: authentication, picks, stage data, results, leaderboard endpoints.
  • Database: PostgreSQL recommended for transactional consistency and strong query support.
  • Jobs/Workers: optional for periodic leaderboard snapshots and cache invalidation.
  • Ops: deploy frontend and API separately, protect internal update routes.

2) Data Model Blueprint

Table Purpose Core Columns
teams Master list of 48 teams id, code, name, group_code, is_active
tournament_stages Stage definitions and active stage id, stage_key, display_name, sequence, is_current
matches Official match results per stage id, stage_id, home_team_id, away_team_id, winner_side, home_score, away_score
users Contest participants id, email, username, created_at
user_picks One rank value per team per user id, user_id, team_id, rank_value, locked_at
score_events Immutable scoring events id, user_id, match_id, team_id, points_awarded, created_at
leaderboard_snapshots Fast read model by stage id, stage_id, user_id, total_points, rank, calculated_at
audit_logs Track dev-team score updates id, actor, action, payload_json, created_at

3) JSON-to-Database Mapping

  • data/teams.json -> seed teams.
  • data/stage-*.json -> seed tournament_stages and matches.
  • data/leaderboard.json -> optional bootstrap for historical display; production leaderboard should come from computed data, not static seed.
  • Browser localStorage values -> migrate to user_picks and authenticated session state.

4) API Contract (Recommended)

Public/User Endpoints

  • GET /api/v1/teams
  • GET /api/v1/stages/current
  • GET /api/v1/stages/{stageId}/matches
  • GET /api/v1/leaderboard?stageId={id}&limit=20
  • GET /api/v1/me/picks
  • PUT /api/v1/me/picks
  • POST /api/v1/me/picks/lock

Internal Dev-Team Endpoints (Protected)

  • POST /internal/v1/stages/{stageId}/activate
  • POST /internal/v1/matches/{matchId}/result
  • POST /internal/v1/leaderboard/rebuild

5) Scoring Logic Placement

Rule Scoring must run on the server only.

  • For each completed match, determine winner side: home, away, or draw.
  • If draw: award 0 points to all users for that match.
  • If winner exists: add that winner team rank value from user_picks.rank_value to each user total.
  • Persist each calculation as a score_events row for traceability.
  • Recompute or incrementally update leaderboard_snapshots.

6) Step-by-Step Implementation Plan

Step 1: Baseline and Freeze

  1. Freeze JSON schema and validate current scoring outputs as reference fixtures.
  2. Document exact stage names and IDs currently used by the frontend.

Step 2: Create Database and Migrations

  1. Create migrations for core tables listed above.
  2. Add unique constraints: one pick per (user_id, team_id), one rank value per (user_id, rank_value).

Step 3: Write Seed/Import Scripts

  1. Import teams and stage results from existing JSON files.
  2. Backfill sample users only in non-production environments.

Step 4: Implement API and Auth

  1. Add user authentication (session or JWT).
  2. Implement picks endpoints and lock endpoint with server-side validation.
  3. Add internal-only endpoints for stage and match result updates.

Step 5: Move Scoring to Backend

  1. Port scoring rules from frontend logic to service layer.
  2. Add deterministic tests against known stage fixtures.

Step 6: Frontend Refactor

  1. Replace all fetch('data/*.json') calls with API calls.
  2. Remove localStorage as source of truth (keep only non-critical UI preferences if needed).
  3. Keep existing UI and contest rules intact while switching data source.

Step 7: Deploy and Cutover

  1. Run dual-read in staging: compare API responses against JSON behavior.
  2. Enable production feature flag for database mode.
  3. Disable JSON endpoints/assets for runtime logic after verification.

7) Example SQL Constraints

-- One rank per team for a user
CREATE UNIQUE INDEX ux_user_picks_user_team
ON user_picks (user_id, team_id);

-- One unique rank value (1..48) per user
CREATE UNIQUE INDEX ux_user_picks_user_rank
ON user_picks (user_id, rank_value);

-- Optional safety check
ALTER TABLE user_picks
ADD CONSTRAINT chk_rank_value_range CHECK (rank_value BETWEEN 1 AND 48);

8) Security and Operations Checklist

Required Minimum production readiness checklist:

  • Protect internal endpoints with role-based access control and IP allow-list if possible.
  • Use parameterized SQL/ORM protections to prevent injection.
  • Add DB backups and restore drill process.
  • Enable structured logs for match updates and score recalculations.
  • Add monitoring for API latency, DB connections, and failed scoring jobs.
  • Use migrations in CI/CD, never manual schema changes in production.

9) High-Risk Areas Found in Current Implementation

  • Client-side scoring and stage control can be manipulated by editing browser storage.
  • Leaderboard values are not authoritative because they are recalculated in the browser.
  • Inline scripts and static data files make auditability and access control difficult.
